# 건축HUB 일시 조회 실패 점검 보고서

- 점검일: 2026-08-24 (Asia/Seoul)
- 대상: 원탑 건축물대장 Streamlit 운영 앱
- 증상: 첫 조회에서 건축HUB 오류가 표시됐지만 같은 조건의 재조회는 성공

## 확인 결과

1. Streamlit 프로세스는 점검 시 정상 실행 중이었고 배포·의존성 초기화 오류는
   없었습니다.
2. Supabase Edge Function의 `/healthz`를 연속 12회 호출한 결과 모두 HTTP 200
   이었습니다. 첫 호출은 702ms, 이후 호출은 43~192ms였습니다.
3. Supabase 대시보드에서 확인 가능한 범위에는 함수 예외가 없었지만, 무료
   로그 화면은 반영에 최대 24시간이 걸릴 수 있어 당시 단일 요청의 정확한
   HTTP 상태는 사후 확정할 수 없었습니다.
4. 코드에서 증상과 정확히 일치하는 자동 복구 공백 두 곳을 확인했습니다.
   - 직접 호출이 연결된 뒤 응답 읽기 단계에서 시간 초과되면 중계로 전환하지
     않고 직접 호출만 반복했습니다.
   - 중계가 일시적으로 타임아웃 또는 503을 반환하면 자동 재시도 없이 즉시
     사용자 오류로 종료했습니다.

따라서 당시 단일 요청의 원문 로그는 보존되지 않았지만, 서버 상시 장애나 키
오류가 아니라 직접 또는 중계 구간의 일시적 전송 지연이 기존 자동 복구 범위를
벗어난 경우로 판단합니다. 인증키·할당량 오류라면 같은 조건의 즉시 재조회가
정상화되는 현상과도 맞지 않습니다.

## 조치

- 직접 연결의 read timeout, 일반 timeout, 응답 중단까지 서울 중계 전환 대상에
  포함했습니다.
- 중계의 전송 오류, 불완전 응답, HTTP 408·429·5xx에 대해 한 번 자동
  재시도하도록 했습니다.
- 재시도마다 타임스탬프와 nonce를 새로 만들어 HMAC 재전송 안전성을
  유지했습니다.
- 중계 요청에는 직접 호출과 분리된 `(연결 5초, 읽기 20초)` 제한을 적용했습니다.
- 실제 재시도가 발생하면 endpoint·원인·상태·시도 횟수를 비밀값 없이
  Streamlit 로그에 남기도록 했습니다.
- 직접 호출의 응답 읽기 지연·응답 중단으로 중계 전환된 경우도 경고 로그에
  남겨 다음 발생 시 구간을 즉시 구분할 수 있게 했습니다.
- 반복 실패 메시지는 자동 재시도까지 완료됐다는 사실을 짧게 표시하도록
  변경했습니다.

## 검증 기준

- 직접 read timeout 후 중계 성공
- 중계 첫 503 후 두 번째 성공
- 중계 첫 read timeout 후 두 번째 성공
- 반복 실패 시 직접 1회 + 중계 2회의 합산 시도 횟수 보고
- 인증·할당량·파라미터 오류는 중계나 반복 요청으로 숨기지 않음

## 남은 제약

외부 공공 API와 무료 실행 환경을 사용하므로 장애 확률을 0으로 만들 수는
없습니다. 다만 기존에는 수동 재조회가 필요했던 대표적인 일시 오류 두 경로를
이번 조치로 한 번의 사용자 조회 안에서 자동 복구합니다.
